Control plane for coding agents · built on OpenCode

Give an agent a goal. Get back verified, reviewable commits.

SAGE is a command-line control plane that runs OpenCode agents under a crash-safe journal, checks every tool call against a policy, and verifies the result with your own tests, which the agent cannot grade or edit.

Coding agents work inside one session. Splitting the goal, isolating each change, checking it and recovering from failures are left to you. SAGE does that work, then waits for you to approve before anything touches your branch.

Get started View on GitHub

TypeScript · Bun · SQLite · no Docker · tested on Windows 11 and Ubuntu

§1The problem

Agents got better at writing code. The work around the code is still manual.

A coding agent can edit, run and debug code inside a session. The lifecycle around that session is still yours to manage. You decide how to split the goal and where each change runs. You check whether the result is actually right, and you clean up when a process dies halfway. Nothing remembers what happened once the session ends. The research behind SAGE points to three gaps in particular.

  1. 19%

    slower: experienced open-source developers using AI tools took 19% longer on real tasks in a randomised trial, while believing they had been about 20% faster. Time shifted from coding to prompting, waiting and reviewing. Becker et al. (METR), 2025, arXiv:2507.09089

  2. tests

    are gameable: when unit tests were altered to contradict the task, so that any pass implies cheating, frontier models still often "passed". Verification run or graded by the agent itself can't be trusted. Zhong, Raghunathan & Carlini, ImpossibleBench, ICLR 2026, arXiv:2510.20270

  3. 1 of 3

    root failure categories of multi-agent LLM systems is task verification and termination. The taxonomy was built from 1,642 annotated traces across 7 frameworks. Cemri et al., Why Do Multi-Agent LLM Systems Fail?, NeurIPS 2025, arXiv:2503.13657

Existing tools each cover part of this: sandboxes in some, hooks and checkpoints in others, event logs elsewhere. SAGE's contribution is putting the missing pieces in one local, model-agnostic tool:

  • a durable task lifecycle;
  • verification the model cannot grade itself;
  • per-task isolation with a policy on every tool call;
  • an append-only trace;
  • human approval gates and cost budgets.

The full gap analysis is in research.md.

§2How it works

A control plane above OpenCode, not a fork of it.

OpenCode does the agent work: providers, the tool loop, LSP, MCP and sessions. SAGE owns everything around a session. It talks to OpenCode in only two ways: the server's HTTP/SSE API, with one opencode serve process per task attempt, and a small guard plugin that sends every tool call to SAGE for a decision.

The run lifecycle

  1. planA planner session reads the repo and returns a task graph. Zod checks it; invalid plans are sent back.
  2. approveYou approve the plan, or pre-approve it with --yes.
  3. executeEach task gets its own worktree, branch and OpenCode process, in dependency order, 2 at a time.
  4. verifySAGE runs your test, typecheck and lint gates and checks the diff for edits to protected files.
  5. approvePassing tasks are merged into a run branch. You review it with sage diff and sage trace.
  6. mergesage merge fast-forwards your branch. Nothing touches it before this step.

Every state change is written to an append-only SQLite journal before its side effect happens. If the process is killed at any point, sage resume continues from the journal and re-runs only a step that was started but not finished.

The model never grades its own work. A task passes only when SAGE's own gates are green and no protected file was changed without permission.

§3What you get

What SAGE gives you, and the gap each one closes.

Runs survive crashes and resume where they stopped.
Run and task state machines sit on an append-only event log, and every transition is journaled before it takes effect. The orchestrator was killed at 7 points in a run, 3 times each; every resume finished without duplicated commits or merges. G1 session-bound execution · G2 unreliable recovery
Every tool call is checked before it runs.
The guard plugin sends each call to SAGE's policy:
  • a path jail around the task's worktree;
  • tests and CI config are read-only;
  • commands go through allow and deny lists;
  • network access is off by default;
  • secret environment variables can't be read.
If SAGE can't be reached, the call is denied. G4 uncontrolled tool access
Tests the agent can't game.
SAGE runs your gates itself, with secrets scrubbed from the environment. It also re-checks the committed diff, which catches a test file edited indirectly by a script the agent wrote and ran. G3 self-graded verification
Nothing reaches your branch without you.
There are two approval gates: the plan, and the merge. An agent can't approve its own work: sage is on the command denylist, approvals are refused inside agent environments, and the journal sits outside every worktree. G5 limited oversight
Spend has a hard ceiling.
Token and USD budgets per task and per run are checked after every model call. Going over interrupts the OpenCode session immediately and escalates the task to you. G7 cost blindness
A full audit trail, down to the file.
sage trace prints goal → plan → task → model calls with tokens and cost → tool calls with policy decisions → diffs → gates → approvals. Every commit carries Sage-Run, Sage-Task and Sage-Step trailers. G5 opaque decisions
Failures are classified, not just retried.
SAGE sorts failures into seven classes. Provider hiccups back off and retry. Red gates retry with the gate output fed back to the agent. Policy violations, conflicts, exhausted budgets and unknown errors each have a defined path, ending with escalation to you. G2 compounding failure
Works with any model OpenCode supports.
Providers come from OpenCode, through its own sign-in or an API key, and SAGE never handles credentials itself. Anthropic models are used with an API key only, not a Claude subscription. G7 vendor lock-in
§4Install

Install and try it without a model.

The commands below are exactly the ones checked in a fresh clone on Windows 11. They work unchanged in Git Bash, PowerShell, and macOS or Linux shells. Where a step differs by platform, both forms are shown.

Prerequisites and tested versions
RequirementTested withNeeded for
git2.55everything
Bun ≥ 1.41.4.4everything
OpenCode 2.x2.3.0, 2.0.29real models only

No Docker, WSL or virtual machine is needed.

Install Bun (skip if bun --version already works)

Windows (PowerShell)

powershell -c "irm bun.sh/install.ps1 | iex"

macOS / Linux

curl -fsSL https://bun.sh/install | bash

or, anywhere with Node.js

npm i -g bun

Clone, install, test, demo

  1. Clone with the OpenCode submodule. sage doctor reads the engine version from it. 
    git clone --recurse-submodules https://github.com/SparshSunilNaik/sage.git
    cd sage
  2. Install dependencies and run the test suite. The tests make no model calls; they use a deterministic fake engine. 
    bun install
    bun test
  3. Check your environment. WARN lines about OpenCode or provider keys are expected until you set up a real model, and they don't block the demo. 
    bun run sage doctor
  4. Create a demo repo wired to the fake engine, run a goal and read its trace. 
    bun run demo
    bun run sage -C .cache/demo-repo run "add multiply and subtract to src/math.ts" --yes
    bun run sage -C .cache/demo-repo trace latest

Point it at your repo and a real model

  1. Install OpenCode 2.x, then either sign in through OpenCode or export a provider key. 
    npm i -g @opencode/cli@2.3.0
    opencode auth login

    or an API key, bash / zsh

    export OPENAI_API_KEY="..."

    or an API key, PowerShell

    $env:OPENAI_API_KEY = "..."
  2. In your repository, create sage.config.jsonc. Replace path/to/sage with your clone. 
    bun path/to/sage/packages/cli/src/bin.ts init
  3. Choose a model and your gates. To use an environment key, list it under passEnv. To use an OpenCode sign-in instead, set "isolateState": false. 
    {
  "engine": {
    "kind": "opencode",
    "model": "openai/gpt-6.1-terra",
    "opencode": { "passEnv": ["OPENAI_API_KEY"] }
  },
  "gates": [{ "name": "test", "command": ["bun", "test"], "parser": "bun-test" }]
}
  4. Check the setup, then run a goal. SAGE stops for your plan approval, and again before merge. 
    bun path/to/sage/packages/cli/src/bin.ts doctor
    bun path/to/sage/packages/cli/src/bin.ts run "your goal"

Provider terms. Anthropic models work through an API key only, not a Claude Pro or Max subscription. ChatGPT and GitHub Copilot work only through OpenCode's official sign-in flows. SAGE never stores or reads credential values.

The full command reference is in the README.

§5Who it's for

Useful when you can say what "done" means in a test.

Good fits today

  • A batch of small, well-specified changes in one repo: new functions with tests, small features, mechanical refactors behind an existing suite. Each runs isolated, gets verified and merges in order, and you approve the whole batch once.
  • Running agents unattended, with guardrails:
    • network off;
    • tests read-only;
    • hard budget stops;
    • unknown commands wait for your decision, or are denied.
    If the machine sleeps or the process dies, sage resume picks the run up.
  • Teams and courses that need an audit trail: which model did what, at what cost, which tool calls were allowed or blocked, and which task every changed file came from.
  • Comparing models on your own tasks: the same goals under different engine.model settings, scored by hidden acceptance tests with sage eval.

Not a good fit yet

  • Large, ambiguous changes that need design judgement. SAGE retries or escalates a failing task; it doesn't re-plan it.
  • Repositories you don't trust. Isolation is at the process and policy level, not a kernel sandbox (see limitations).
  • Projects without automated checks. The gates are the source of truth, and a run where no tests ran counts as a failure.
  • Fast-moving target branches. Merge is fast-forward only.
  • Shared or server deployments. SAGE runs on one machine, and the CLI process is the orchestrator.

§7Limits & safety

What SAGE does not do (yet).

  • Isolation is at the process and policy level, not the kernel. There are no containers or VMs. If an agent writes a program and runs it with an allowed interpreter, that program runs with your user's privileges. SAGE limits the damage with a scrubbed environment, the verifier's tamper check, the merge gate and the trace, but it can't prevent it.
  • "Network off" applies to tools and commands only. There is no firewall.
  • Merge is fast-forward only. If your branch moved during the run, you merge the run branch yourself.
  • No re-planning after a failing task. Failures are retried, with feedback, or escalated to you.
  • No SWE-bench run, and the full live evaluation is still pending.
  • One machine, one user. There is no daemon; sage resume restarts the orchestrator.

Read the threat model for exactly what is and isn't protected, and PROGRESS.md for known issues and next steps.
